# Relocate the standalone work record into each rulebook repository

## 1. Intent

The work record for building the four new per-role rulebooks (`product`,
`feasibility`, `review`, `ops`) was written under a newly created standalone
repository, `/home/jwjung/tokenmaxxxer/` itself (a bare top-level `docs/`
tree with its own `.git` and a `.gitignore` that exists only to support it).
That standalone repository was never asked for. The user's actual
instruction was that each rulebook repository carries its own record of the
work done in it. This proposal relocates every proposal, hunt report,
review, research file, and spec currently under
`/home/jwjung/tokenmaxxxer/docs/` into the rulebook repository (or
repositories) whose work it describes, then removes the standalone
repository, leaving the four rulebook repos and the two protected,
untouched repos (`coding-agent-rulebook`, `qa-agent-rulebook`) as the only
git repositories under `/home/jwjung/tokenmaxxxer/`.

Correction to a phrase in the frontmatter `files:` list above: the line
naming `coding-agent-rulebook/docs/proposals/2026-07-25-product-agent-rulebook-repo.md
(SKIPPED …)` is not a real destination — `coding-agent-rulebook` is
out-of-bounds and nothing is written there. That entry exists only so a
reader scanning the write set sees that this file was explicitly considered
and its destination is `product-agent-rulebook`, not `coding-agent-rulebook`;
delete that line before treating the frontmatter as literal — see §3, row for
`2026-07-25-product-agent-rulebook-repo.md`.

## 2. Constraints that change what gets built

- Every rulebook repo is self-contained: it carries its own copy of the
  record for work done in it. A document describing work in several repos
  gets a byte-identical copy in each of those repos — no shared file, no
  cross-repo symlink, no cross-repo link.
- Destinations are, per repo: `docs/proposals/`, `docs/reports/` (with
  research under `docs/reports/research/<same-subdirectory-name>/`), and
  `docs/specs/`. Filenames are unchanged. Any bucket a target repo does not
  yet have is created (`mkdir -p`) as part of the copy, not left for the
  first file to implicitly create.
- The reason for the relocation: a commit's `Proposal:` trailer names a path
  inside the same repository as the commit, so `git log --grep` and the
  named file live together in one `git log`/`git show` — not split across a
  now-deleted fifth repository.
- `coding-agent-rulebook` and `qa-agent-rulebook` are out of bounds: nothing
  is copied into them, nothing in them is edited, nothing in them is
  deleted. The two review reports in the standalone repo that describe
  those two repos (§3) are relocated as reference material into the four
  in-scope repos — the review files themselves move, the repos they
  describe are never touched.
- Role state files (`state.md` / `state.json` under each `*-cycle` plugin's
  runtime workspace) stay gitignored runtime artifacts. Nothing about them
  changes.

## 3. Routing table

Rule key (cite the letter in the "rule" column):

- **(A)** A proposal goes to every repo named anywhere in its own
  frontmatter `files:` write set (repo-prefixed paths, e.g.
  `product-agent-rulebook/...`).
- **(B)** A hunt/review report goes to every repo its own proposal went to
  (via its `proposal:` frontmatter field or in-body reference). A report
  with no proposal (a read-only review) goes to every repo it functioned as
  reference material for.
- **(C)** A research file goes to every repo whose role it is cited under
  in `docs/specs/agent-roles.md`, or, if cited only as a general source with
  no role-specific paragraph, to all four in-scope repos.
- **(D)** `docs/specs/agent-roles.md` describes all four new roles (plus
  the two existing, unchanged, out-of-bounds roles) — it goes to all four
  in-scope repos, never to the two protected repos.
- **(E)** This proposal document itself describes work across all four
  repos (the relocation and the standalone-repo removal), so — per the same
  rule as (A) — it gets a copy in each of the four repos, which is also what
  makes each repo's own `Proposal:` trailer resolve to a file inside that
  same repo.

1. **Copy first.** For each row above, create the destination bucket

2. **Verify.** Confirm, for every row, that the file is present at its

   copy, not a rewrite). Only proceed to step 3 once every row passes.
3. **Remove the standalone repository**, in two steps, only after step 2
   passes:
   - `gh repo delete tokenmaxxxer/tokenmaxxxer` — removes the GitHub
     remote.
   - Remove the local `/home/jwjung/tokenmaxxxer/.git` directory and the
     root `/home/jwjung/tokenmaxxxer/.gitignore` (it existed only to serve
     this standalone repo's git tree). The working-tree `docs/` files under

     — this build copies them out but does not delete the originals — so no
     document is lost by either half of this removal.
4. **Per-repo commit.** In each of the four rulebook repos, on its own
   branch, commit only the files this table routed to that repo, with a
   message body describing what record was added (which proposals, which
   reports, which research files, which spec) and ending with exactly:

   already copied this proposal file there — that resolution, not merely
   having a trailer, is the point of the whole relocation.
5. **Landing, per repo, follows the dispatch flow already in use**: an
   issue recording the requirement, a branch, a PR whose body includes
   `Closes #<n>`, an approval-quote comment, and a merge only once the user
